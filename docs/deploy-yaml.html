deploy.yaml 规范

每个仓库根目录放一个 deploy.yaml（或 deploy.yml），声明构建与运行方式； 推送到部署分支后由流水线执行，产物自动发布为站点或托管为常驻服务。

总览

三种部署类型：static（纯前端 → /sites/<仓库>/）、service（后端服务 + 可选前端）、 dual（前端与后端两个产物）。未知字段会被直接拒绝（防止拼写错误静默失效）。

字段类型说明
typestring 必填static｜service｜dual
envmap 可选顶层环境变量：构建与服务进程共用，run.env 可覆盖
build.frontendobject 可选前端构建（static 可选、dual 必填、service 可选）
build.backendobject 可选后端构建（service / dual 必填）
runobject 可选服务启动方式（service / dual 必填）
static_serverobject 可选仅 dual：SPA 开关 / 前端目录覆盖
同一仓库内任务串行、跨仓库并行；相同 commit 的重复推送会合并。deploy.yaml 只从部署分支的最新提交读取， 也可以在仓库页手动「重新部署」或部署历史提交（回滚）。

type：部署类型

值产物访问方式必填
static静态文件目录/sites/<归属_仓库>/无（零配置即可）
service常驻进程（可带前端）自动分配端口；经 /api/<归属_仓库>/ 反代build.backend + run
dual静态前端 + 常驻后端前端 /sites/…/，后端 /api/…/build.frontend + build.backend + run
互斥规则：static 不能写 build.backend / run / static_server； service 不能写 static_server；dual 的 static_server 可选。

env：环境变量

写在顶层，构建命令与服务进程都会继承；run.env 叠加在其上（同名覆盖）。

env:
  APP_ENV: production
  GOPROXY: https://goproxy.cn,direct   # 服务器无外网时给 Go 构建用
run:
  command: ./app
  env:
    GOMEMLIMIT: 256MiB                # 只给服务进程
平台还会自动注入：构建与服务都有的 GITWO_REPO / GITWO_BRANCH / GITWO_COMMIT / GITWO_TASK / TMPDIR； 服务进程另有 PORT 与 GITWO_PORT（见下文「run」）。 平台不会安装任何语言工具链，环境需提前预装（systemd 运行时记得在 unit 里补 Environment=PATH=…）。

build：构建

命令用 sh -c 执行，支持 &&、管道等；默认在仓库根运行，可用 dir 切到子目录。

build.frontend

字段必填说明
command可选前端构建命令（如 npm ci && npm run build）。留空 = 原生静态目录：跳过构建直接发布 output
dir可选命令运行目录（仓库内子目录，如 web）
output必填构建产物目录，相对仓库根（绝对路径也可）。原生静态且零配置时缺省为仓库根 .
target可选发布目标目录，缺省 <程序目录>/apps/<归属_仓库>/static；自定义时建议写绝对路径，不能落在仓库工作区内
verify_index可选发布后校验 index.html 是否存在，缺省跟随 server.yaml 的 verify_index（默认 true）
发布时会排除 .git 与 deploy.yaml；发布方式为 rsync -a --delete（无 rsync 时用内置镜像）， 所以 target 里的旧文件会被清理，别指向有其它内容的目录。

build.backend

字段必填说明
command必填构建命令；常见 go build -o bin/app ./cmd/server、mvn -q package -DskipTests、python3 -m compileall …
dir可选命令运行目录（仓库内子目录）
output必填构建产物（单个文件），相对仓库根；构建后必须存在
构建环境：TMPDIR 指向任务独立临时目录；每条 build 命令有总超时（timeouts.build，默认 10m） 与停滞检测（连续 20s 无输出且整棵进程树几乎不占 CPU 即判定卡死，timeouts.stall 可调，0 关闭）。 进程以独立进程组运行，超时会整组终止。

run：服务启动

字段必填说明
command必填启动命令，如 ./app、java -jar app.jar、venv/bin/python app.py。第一个词用于 PID 归属校验
workdir可选服务运行目录，缺省 <程序目录>/apps/<归属_仓库>/；二进制、app.pid、app.log、backups/ 与 run.files 都落到这里
port可选显式监听端口；缺省自动分配（server.yaml 的 20000-23999）并注入 $PORT，下次部署沿用上次端口，站点地址不漂移
env可选只注入服务进程的环境变量（叠加在顶层 env 之上）
keep_binaries可选在 backups/ 保留最近 N 个旧二进制（0 = 不保留，缺省）
files可选运行所需的非二进制文件/目录，见下文「run.files」
服务必须读取 $PORT 监听（显式 run.port 时两处保持一致）。启动流程： 原子替换二进制（temp + rename，避开 text file busy）→ 读 app.pid 并用 /proc 校验进程归属防误杀 → SIGTERM 等待（timeouts.stop，默认 15s）→ 超时 SIGKILL → setsid nohup 启动 → 2s 存活确认（死亡自动附 app.log 尾部）。进程独立于 gitwo，重启平台不影响已部署服务。
服务的工作目录就是 run.workdir（缺省 <程序目录>/apps/<归属_仓库>/）， 不会从仓库工作区读取任何文件。运行期需要的配置文件/资源（如 config.yaml）必须用 run.files 同步到运行目录；也不要为了“就近读配置”把 run.workdir 指到工作区—— 工作区每次部署都会 git checkout + git clean -fdx，会清掉 app.pid / app.log， 导致旧进程停不掉、端口冲突。

run.files：解释型语言与配置文件

把仓库里运行所需的文件/目录同步到服务运行目录（二进制由平台自动安装，不需要列）。服务从运行目录启动、工作区只用于构建且每次部署都会刷新，所以运行时读取的文件必须在这里列出。

规则说明
相对仓库根解析条目相对该提交的构建工作区根目录（<程序目录>/workspaces/<归属_仓库>/，与 deploy.yaml 同级），不是相对 build.backend.dir 或 run.workdir
单文件 → 运行目录根只保留文件名，如 files: [configs/config.yaml] 会变成运行目录下的 config.yaml；要保留子目录结构请写目录条目 files: [configs]（按相对路径整体镜像）
只同步已提交内容每次部署先 git checkout 再 git clean -fdx，工作区里只有提交过的文件；只在本地或被 .gitignore 忽略的配置不会被同步
可以列构建产物构建期生成的文件也可以列（该步骤在构建、二进制安装之后执行）
 
run:
  command: ./app
  files: [config.yaml]          # 仓库根 config.yaml → 运行目录/config.yaml
  # files: [configs]            # 目录整体镜像 → 运行目录/configs/...
  # files: [bin/config.yaml]    # 构建产物 → 运行目录/config.yaml（单文件取文件名）
工作区（workspaces/…）与运行目录（apps/…）是两个不同目录：部署时二进制会被安装到运行目录， 服务也在运行目录启动（cwd），不会回工作区找文件。因此运行期要读的配置/资源必须列进 run.files； 也不要把 run.workdir 指到工作区，否则下次部署的 git clean -fdx 会清掉 app.pid / app.log，旧进程停不掉并造成端口冲突。
报 run.files entry "…" not found in repo：先确认文件确实在仓库里且已提交（git ls-files | grep config）， 再检查是否在子目录（路径要写全）或其实是构建产物。

static_server：SPA 与前端目录覆盖（仅 dual）

字段缺省说明
spatrueSPA 回退：未知路径回落到 index.html（history 路由需要）。type: static 的站点默认开启且不可关闭
static_dirapps/<归属_仓库>/staticdual 模式下的前端发布目录覆盖（等价于 build.frontend.target）
addr—仅记录用（独立静态服务器工具的参数），平台托管不使用

执行环境与行为

项目说明
数据目录程序所在目录（或 -home / GITWO_HOME）：repos/ workspaces/ apps/ data/；临时文件在 /tmp/gitwo/
构建工作区<程序目录>/workspaces/<归属_仓库>/，每次部署 checkout 到指定 commit 并 git clean -fdx
服务目录<程序目录>/apps/<归属_仓库>/（run.workdir 可改）：gitwo 安装的二进制、app.pid、app.log、backups/
端口显式 run.port 或自动分配（20000-23999，可配），注入 PORT / GITWO_PORT；启动前探测占用，下次部署沿用
超时server.yaml 的 timeouts：git 5m / build 10m / deploy 5m / stop 15s / start_wait 2s / stall 20s
日志任务日志 /tmp/gitwo/logs/<归属_仓库>/<task>.log（流水线页实时查看，每仓库保留最近 20 份）；服务日志 app.log（运行目录，仓库页「运行日志」可分页查看，仅开发者/管理员）
单进程限制一个仓库一个服务进程；构建与启动命令以 gitwo 运行用户身份在宿主机执行——能 push 即等同该用户命令执行权限

语言示例

以下示例都放在仓库根目录；改命令与路径即可适配你的项目结构。

Go 服务（多包，推荐）

单二进制，不需要 run.files；程序读取 $PORT 监听。

type: service

env:
  CGO_ENABLED: "0"

build:
  backend:
    command: go build -trimpath -ldflags "-s -w" -o bin/app ./cmd/server
    output: bin/app

run:
  command: ./app
  files: [config.yaml]        # 需要在运行目录读配置文件时

Go 服务（单文件）

只有 main.go、无 go.mod 的小工具也能用；构建产物名与 run.command 保持一致。

type: service
build:
  backend:
    command: go build -o app ./main.go
    output: app
run:
  command: ./app

Python（venv + pip）

构建期创建虚拟环境；venv 目录与脚本通过 run.files 同步到运行目录，启动时用运行目录内的解释器。

type: service

env:
  PIP_INDEX_URL: https://pypi.tuna.tsinghua.edu.cn/simple

build:
  backend:
    command: python3 -m venv venv && venv/bin/pip install -r requirements.txt && echo ok > venv/.built
    output: venv/.built

run:
  command: venv/bin/python app.py
  files: [app.py, requirements.txt, venv]
服务器需预装 python3 与 pip；纯脚本无依赖时直接用 files: [app.py] + command: python3 app.py。

Java（Maven → jar）

jar 会被安装到运行目录；用 run.files 同步子目录时保留结构。

type: service

build:
  backend:
    command: mvn -q -DskipTests package
    output: target/app.jar

run:
  command: java -jar app.jar
  files: [config]              # 目录整体镜像 → 运行目录/config/...
  port: 8080

原生静态页面（零配置）

不写 build 段：仓库根目录即站点，直接发布，index.html 必须在根目录。

type: static

静态文件在子目录（如 public/）时，留空 command 只发布该目录：

type: static
build:
  frontend:
    output: public

Vue / Vite 单页应用（SPA）

构建后发布 dist；静态站点默认开启 SPA 回退，history 路由可直接刷新。

type: static
build:
  frontend:
    command: npm ci && npm run build
    output: dist
    verify_index: true
    # dir: web                 # package.json 在子目录时
前端框架不限（Vue/React/Angular/Svelte…），只是构建命令与产物目录不同；需要后端 API 时见下面的 dual。

前后端分离（dual）

前端发布到 /sites/，后端经 /api/ 反代，共用一个 9527 端口。

type: dual

env:
  APP_ENV: production

build:
  frontend:
    command: npm ci && npm run build
    output: dist
  backend:
    command: go build -trimpath -ldflags "-s -w" -o bin/api ./cmd/api
    output: bin/api

run:
  command: ./api
  files: [configs]
  env:
    GOMEMLIMIT: 256MiB

static_server:
  spa: true

常见报错对照

报错原因 / 处理
no deploy.yaml仓库根目录没有 deploy.yaml；或部署分支不对（仓库设置里确认）
backend binary ... not found after build构建命令失败或 output 路径写错（注意是相对仓库根）
frontend output ... not found构建产物目录不存在：检查 command 是否成功、output 是否对
index.html missing in ...产物目录里没有 index.html（路径不对或构建失败），或设 verify_index: false
run.files entry "…" not found in repo见下文「run.files」：文件不在仓库根/未提交/在子目录/是构建产物
停滞超过 20s（无输出且几乎无 CPU）构建卡在依赖下载/网络：给运行用户配 GOPROXY（如 goproxy.cn）或 go mod vendor；也可调大 timeouts.stall
执行超时构建确实超过 timeouts.build（默认 10m）：调大超时或预热依赖缓存
service exited immediately after start启动即崩：详情页日志会附 app.log 尾部，多为端口/配置/依赖问题
pid N currently runs "xxx", refusing to killapp.pid 指向了别的进程（PID 复用）：人工清理 app.pid 后再部署
port ... already in use旧进程未退出或显式端口被占：检查 run.port 与进程
